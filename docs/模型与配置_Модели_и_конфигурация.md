# 模型与配置（Модели и конфигурация）

本文说明系统里**哪些部分属于"模型"**、各自用什么算法、参数在哪里、如何切换与复现。
结论先说：项目**不包含本地神经网络权重**，不需要 GPU，也不需要下载模型文件；
"判定"完全由规则引擎完成，"措辞"才由外部大模型负责。

---

## 一、四层结构，只有最上面一层是"大模型"

| 层 | 文件 | 是什么 | 是否调用网络 |
|---|---|---|---|
| 1. 知识库（判定依据） | `data/cn_standards_final.json`、`data/ru_standards.json` 等 | 中俄规范条款数字化：中国 9 项标准、俄罗斯 14 项标准 + 2 部技术法规 → **181 项受控特征**，每项要求归入 **10 种要求形式**之一 | 否 |
| 2. 判定（规则引擎） | `engine/evaluate.py` | 确定性规则：逐项判定 通过／不通过／数据不足；ТР ТС 032/2013 按 P×DN 判类别，ТР ЕАЭС 043/2017 按用途判适用；覆盖率 < 50 % 时不给类别（NA） | 否 |
| 3. 检索（对话入口） | `engine/rag_chat.py` | 查询理解与路由 → **BM25**（`k1 = 1,5`、`b = 0,75`，词频饱和 + idf + 长度归一）→ 字段加权 + 标准号/短语**重排** | 否 |
| 4. 表达（可选大模型） | `engine/llm_report.py` + `engine/agent_prompt.md` | 把第 2 层的结构化判定写成成文报告；**不参与判定** | 是（可关闭） |

模型解析层（不属于以上四层，但同样确定性）：`engine/ifc_pipe.py`（IFC2X3 / IFC4 解析）、`engine/model_page.py`（三维标注与结论页）。

> 换句话说：**换一个语言模型，结论不会变**——变的只是表达。这是系统可审计、可复现的前提。

---

## 二、用到的大模型与参数

| 参数 | 值 | 位置 |
|---|---|---|
| 接口协议 | OpenAI 兼容 `/chat/completions`（标准库 `urllib`，无额外依赖） | `engine/llm_report.py:71-95` |
| 默认供应商地址 | `https://api.deepseek.com/v1` | `LLM_BASE_URL` |
| 默认模型 | `deepseek-chat`（任何 OpenAI 兼容模型均可：Qwen、GLM、Kimi 等） | `LLM_MODEL` |
| temperature | **0,2**（写死在代码里，不通过环境变量配置） | `engine/llm_report.py:83` |
| 超时 | 120 с | `engine/llm_report.py:92` |
| 提示词 | 系统提示 `engine/agent_prompt.md` + 用户消息由规则引擎结果拼装 | `engine/llm_report.py:59`（`_build_prompt`） |
| 调用范围 | **仅报告模块**。对话入口（`rag_chat.py`）与 IFC 分析（`ifc_pipe.py`）不调用大模型 | — |

## 三、环境变量

见 `deploy/aliyun/.env.example`（模板，不含真实密钥）：

```ini
# 报告层
LLM_PROVIDER=mock                  # mock = 不联网，模板报告；openai = 调真实模型
LLM_BASE_URL=https://api.deepseek.com/v1
LLM_API_KEY=                       # 真实密钥只放在服务器 /etc/cnru-fire-pipe/env
LLM_MODEL=deepseek-chat

# 企业微信推送
WC_CORP_ID=
WC_AGENT_SECRET=
WC_AGENT_ID=
WECHAT_DRY_RUN=1

# 数据目录
DATA_DIR=/opt/cnru-fire-pipe/data
```

**密钥绝不入库**：`.env`、`*.pem`、`*.key` 已在 `.gitignore` 中排除；服务器上密钥保存在 `/etc/cnru-fire-pipe/env`，由 systemd 的 `EnvironmentFile` 注入。

## 四、当前部署状态（须知）

演示站 `http://47.94.235.211` 的运行环境为：

```
LLM_PROVIDER=mock
LLM_API_KEY=（空）
```

也就是说**线上报告由规则引擎结果 + 模板生成，不调用大模型**。判定、对话、IFC 分析的结果与真实模型模式一致（因为它们本来就不用大模型），差别只在报告的措辞风格。

切换到真实模型只需两步（无需改代码）：

```bash
# 1) 写入密钥
echo 'LLM_PROVIDER=openai' >> /etc/cnru-fire-pipe/env
echo 'LLM_API_KEY=sk-...' >> /etc/cnru-fire-pipe/env
echo 'LLM_MODEL=deepseek-chat' >> /etc/cnru-fire-pipe/env

# 2) 重启
systemctl restart cnru-api
```

本地验证同样简单：

```bash
python engine/llm_report.py examples/sample_input_firepipe.json                 # mock
python engine/llm_report.py examples/sample_input_firepipe.json --provider openai
```

## 五、为什么不用"纯大模型"

| 风险 | 纯 LLM 方案 | 本项目 |
|---|---|---|
| 结论不稳定 | 同一输入两次可能给出不同判定 | 判定由规则引擎给出，同一输入结论恒定 |
| 无法追溯 | 无法说明依据哪一条 | 每条结论带标准号 + 条款号 |
| 编造条款 | 常见 | 条款只来自 `data/*.json`，不生成 |
| 数据不足时 | 倾向于"猜一个结论" | 覆盖率 < 50 % 直接返回"数据不足"，不猜 |
| 成本与合规 | 每次调用都要外发数据 | 默认 mock 模式完全离线；对话与 IFC 分析不外发 |

## 六、如需私有化 / 离线部署

三种选择，都不需要改业务代码：

1. **保持 mock 模式**——完全离线，报告为模板，合规性最强；
2. **本地推理服务**：用 vLLM / Ollama / Xinference 暴露 OpenAI 兼容端口，然后
   `LLM_BASE_URL=http://127.0.0.1:8001/v1`、`LLM_MODEL=<本地模型名>`；
3. **换供应商**：任何 OpenAI 兼容接口（通义千问、智谱 GLM、Kimi、OpenAI 官方）只改 `LLM_BASE_URL` + `LLM_MODEL` + 密钥。

## 七、复现性检查清单

- [ ] 同一 `examples/sample_input_firepipe.json` 运行两次 `engine/evaluate.py`，判定完全一致（规则引擎，确定性）
- [ ] `mock` 与 `openai` 两种模式的**判定字段**逐项一致，仅报告措辞不同
- [ ] 每条结论都能在 `data/*.json` 中找到对应条款记录
- [ ] 抽查覆盖率 < 50 % 的样本，确认返回"数据不足"而非某个类别
